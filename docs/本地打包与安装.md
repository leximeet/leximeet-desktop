# 本地打包与安装

Desktop 1.0.0 把前端、Electron 主进程、固定 Core Jar、裁剪 Java 21、Native Host 和 Dictionary Core Text 打成同一应用。使用者不需要另装 Java；开发者打包需要 JDK 21。

## 准备

从 Desktop 仓库根目录操作，需要 Node.js 24+、npm、JDK 21、Maven 3.9+、Python 3。请使用目标平台和目标架构的机器构建：例如 Apple Silicon + arm64 Node + arm64 JDK 生成 macOS arm64 安装包，不能把本机 JRE 塞进另一个平台的包。

```bash
git submodule update --init core-java
export JAVA_HOME=/path/to/jdk-21
export PATH="$JAVA_HOME/bin:$PATH"
npm ci
```

macOS 的隔离安装测试还需要 Xcode Command Line Tools（`xcrun swiftc`），用于只读系统焦点监测；不需要辅助功能或录屏权限。缺少工具会在应用启动前明确报错，不自动打开系统安装窗口。

Maven 不在 PATH 时设置 `LEXIMEET_MAVEN` 为其可执行文件的绝对路径。准备资源只下载锁定版本；不会把相邻词典开发仓库的未发布数据混入安装包。`JAVA_HOME` 同时用于 Core 和 jlink，脚本检查实际 Java 主版本与 CPU 架构。

## 一条命令生成并验收

先提交当前 Desktop 和 Core 改动，确认 Core checkout 等于 Desktop 的 gitlink，然后执行：

```bash
npm run release:local
```

命令依次完成：格式与文档检查 → 冻结协议校验 → 单元及 Core 测试 → 当前源码构建 → 本机安装器 → 实际物料核对 → Core SBOM/许可核对 → 隔离安装后的应用启动、练习与重启恢复。测试使用临时安装目录与空白资料，隐藏、静音，不覆盖 `/Applications`，也不读取或清理日常学习资料。

macOS 输出 DMG 和 ZIP；Windows 为 NSIS，Linux 为 AppImage。**目前完整实机验证是 macOS arm64。** Windows 安装自动测试只能在一次性 VM 或 GitHub 托管 runner 运行；配置存在不等于该平台验收通过。

只需要调试应用目录时可执行 `npm run package:dir`；只构建分发文件可执行 `npm run package:dist`。这两条命令允许未提交源码，清单会如实记录 `dirty`，并将启动验证标为 `not-run`，不能据此宣称完成安装验收。

## 去哪里找文件

默认每次使用一个新的目录：

```text
release/1.0.0/darwin-arm64/<构建时间>/
  LexiMeet-1.0.0-mac-arm64.dmg
  LexiMeet-1.0.0-mac-arm64.zip
  mac-arm64/LexiMeet.app
  BUILD-MANIFEST.json
  SHA256SUMS
```

`BUILD-MANIFEST.json` 记录应用版本、Desktop/Core 提交与 dirty 状态、Java 版本、规范摘要、词典清单、实际 Jar/ASAR 摘要、安装文件字节大小及验证范围。`SHA256SUMS` 是本轮安装文件的校验和。最后一次完整构建的位置记在 `.runtime/current-package.json`；测试默认读取它，不遍历旧 `release` 猜哪一份最新。

```bash
node scripts/artifacts.cjs find-installer
node scripts/artifacts.cjs find-executable
node scripts/verify-package-materials.cjs
```

可通过 `LEXIMEET_BUILD_OUTPUT` 指定新的空目录；目录非空会拒绝构建，不删除已有文件。候选版本可用 `LEXIMEET_BUILD_VERSION=1.0.1-rc.1`，这只改变安装物版本，不修改源码版本。临时版本号不表示资料格式发生升级。

## 配套完整源码

分发候选时同时提供 Desktop 和固定 Core 的完整对应源码。托管平台的单仓源码包不能作为已包含 `core-java` 的完整源码证明；`sources.jar` 也不含构建、资源及测试，不能单独替代。先从本轮 `BUILD-MANIFEST.json` 读取两个 `sources.*.commit`，然后固定这两个提交归档：

```bash
git archive --format=tar.gz --prefix=leximeet-desktop/ \
  --output=/path/to/output/leximeet-desktop-source.tar.gz <desktop-commit>
git -C core-java archive --format=tar.gz --prefix=leximeet-desktop-core/ \
  --output=/path/to/output/leximeet-desktop-core-source.tar.gz <core-commit>
```

归档包含自有源码、构建配置、锁文件、测试、规范快照与许可；可以重新下载的大词典由资源准备脚本锁定版本和校验值。另附 `SOURCE.json` 与 `SOURCE-SHA256SUMS`，记录源码提交及归档摘要，安装文件仍以 `SHA256SUMS` 为准。后续只修改文档或测试的提交应另行说明，不能直接把 HEAD 当作已有安装器的实际编译来源。

## 本机安装

1.0.0 首次运行使用新的稳定资料空间。macOS 为 `~/Library/Application Support/LexiMeet/workspaces/v1`，开发运行使用项目 `.runtime/dev-v1`。以前的未发布试用库保留原位置，不读取、不迁移、不删除。此 `v1` 是正式资料空间标识，后续已发布版本沿用并按实际格式维护升级；不是每次发版换一个空目录。显式设置 `LEXIMEET_DATA_DIR` 时仍使用指定位置，测试环境继续每次独立。

退出正在运行的词遇，打开**本轮目录内的 DMG**，把其中的 `LexiMeet.app` 放入应用目录。检查系统里是否还有其他同名旧副本；Dock 可能仍指向旧路径，应从新安装的位置打开。ZIP 是同一构建的压缩应用，`.app` 是展开应用，大小不能直接比较。

当前 macOS 构建使用 ad-hoc 签名，未进行 Developer ID 公证；正式分发前须单独完成签名、公证、系统权限和安装检查。不要全局关闭 Gatekeeper。`release:local` 只产生本地文件，不创建 Git tag、推送、Release 或商店提交。

## 启动报错怎么办

| 提示                                  | 处理                                                                   |
| ------------------------------------- | ---------------------------------------------------------------------- |
| `BeanCreationException`，界面仍是旧版 | 核对应用位置与包内版本，安装同一轮的新 DMG；旧包不会因源码更新而更新   |
| 数据格式不受支持                      | 保留资料文件，使用匹配的应用；未发布的 0.x/rc 测试库不自动迁移到 1.0.0 |
| 当前格式缺少必要表 / 数据文件损坏     | 保留文件，使用有效备份恢复到独立空间；不要改 schema 数字或清库绕过     |
| 需要 Java 21 / 随包运行时缺失         | 重新生成完整安装物，不能只复制前端或 Jar；使用者不需要另装 JDK         |
| 没有完整构建 / 物料与来源不同         | 重新打包，不把旧 DMG、新 `.app` 与另一份 Jar 混用                      |

启动错误提供固定的安全分类与操作建议，不将令牌、SQL、笔记或私人路径直接显示到页面。未知格式拒绝并保留。开发验收可用 `bash scripts/test-desktop.sh` 创建新资料；正式 1.0.0 发布以后才维护已发布版本的升级承诺。

## 正式发布前还需要什么

完整对应源码必须同时包含 Desktop 和固定 gitlink 的 Core；托管平台自动生成的 Desktop 源码压缩包不能替代 Core 对应源码，应单独核对是否包含子模块内容。分发产物需保留运行库、词典、图标与音效的许可通知，参考[安全与许可](安全与许可.md)。远端 CI、公开历史审阅、正式签名/公证，以及通知/快捷键/声音的人工验收，均需分别记录，本地构建成功不能替代这些检查。

`candidate.yml` 人工触发后只上传测试候选与源码，不自动发布。正式发布授权与路线见[发布与路线图](发布与路线图.md)。

## 首次源码发布

软件源码标签为 `1.0.0`。首次公开的 main 保留远程原始 init commit，并将其后的开发工作整理为一个完整结果提交；开发历史备份保留在本地，不随公开分支推送。整理历史不会删除当前源码或许可证，也不会改变协议语义。

首次历史整理已经完成，后续正常提交，不重复压缩 main。标签尚未公开时可继续修改，最终验收通过后再创建注解标签 `1.0.0`；版本字段为 1.0.0 不表示标签或发行物已经发布。已公开的标签不移动，后续修复使用新版本。

GitHub 与 Gitee 平级。分别核对两端 main 后，先发布 LMCP 与 Core，再发布 Browser 与 Desktop，确保 Desktop 固定的 Core gitlink 在两个平台都可获取。同一版本向两端推送**同一个本地注解标签**，不分别创建同名标签；标签对象、源码提交与发行文件 SHA-256 应一致。两个平台下载同一轮已验收产物，不为了第二个平台重新构建。

维护者明确授权后才执行各平台的推送和 Release 操作。仅推送所需 main 和版本标签，不使用强制推送、`--all` 或 `--mirror`；本地开发历史备份不公开。远端出现新提交时先审阅、整合并验证，不用一个平台覆盖另一个。代码推送、Actions artifact、正式安装包上传是不同步骤，完成一项不能代替其余项。
