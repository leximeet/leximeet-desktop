# 日常使用与升级测试

## 为什么分三段

短单元测试验证算法边界，核心场景则检查用户连续使用后，资料与操作是否仍然一致。三段独立报告失败并保留各自的检查点，避免把七天循环放进一个难以定位问题的巨型测试。

| 阶段     | 要检查的事情                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------- |
| 首次安装 | 空资料与默认设置、欢迎教学、可选目标/计划、实际临摹完成后继续教学，再回练习重开                         |
| 七天使用 | 学三天、休一天、再学三天；六种模式、状态、重开/连续操作、目标和笔记、采集及通知练习；每天记录数据检查点 |
| 候选升级 | 旧候选真实应用写资料，退出后用新的不同版本应用/不同 Jar 打开同一隔离目录，再继续练习与采集              |

七天只推进测试业务 Clock，不改 macOS 时间，不全局替换 Date。学习日、计分保护/衰减、计划、采集窗口与学习提醒共用业务时间；授权、会话、限流、网络超时继续使用真实时间。时钟文件只允许显式 test profile 内 core/test-clock.json，正式环境拒绝。通过测试 helper 原子写入 `{instant,zone}`，并核对 Core 返回日期，避免页面假装到了明天。

通知在隐藏、静音的系统适配器中触发，真正经过 Main、Core 判题、幂等和 SQLite。自动调度与答题分别断言；系统可见横幅和许可另行人工检查。后台测试不使用操作者键鼠、剪贴板或日常浏览器。

## 运行和迭代

在仓库根目录执行首启和七天场景：

```bash
bash scripts/test-desktop.sh --journey
```

入口自动准备 Node/JDK/Maven、固定资源及当前 Source，降低进程优先级后启动隐藏、静音的测试。已有冻结构建可附加 `--prepared` 避免重复构建；`--check` 只读检查，不启动应用。Source 默认共七项：初始化、普通/教学练习回归、七天、跨天回执恢复、明/暗视觉。报告包含用例指纹、每天检查点和焦点证据。

跨天恢复专项让真实 Core 完成保存后，仅丢弃一次 Main 回执。第二天重新打开同一资料，重试必须沿用原提交身份，不能再加分；重新开始后才创建合法新一轮。它与普通七天场景分开，失败能直接定位。

普通练习回归还在提示扣分确认后拒绝一次题目读取；「重新读取提示」必须只重读原题，不能生成第二条扣分事实。故障仅注入本轮隐藏应用的 IPC handler，测试结束还原，不伪造 Core 成功结果。

教学回归还检查另一种失败：真实练习已经计分，但随后确认草稿写入失败。教学仍留在临摹步骤，用户能实际点击恢复按钮；以原提交身份恢复后，SQLite 仍只有一条练习，再继续教学。不能只断言按钮存在或用脚本绕过教学的操作隔离。

真实候选包使用绝对**可执行文件**路径（macOS 为 `.app/Contents/MacOS/LexiMeet`）：

```bash
bash scripts/test-desktop.sh --journey --package "/path/to/New.app/Contents/MacOS/LexiMeet"
bash scripts/test-desktop.sh --journey --upgrade "/path/to/Old.app/Contents/MacOS/LexiMeet" "/path/to/New.app/Contents/MacOS/LexiMeet"
```

两份包必须存在且不同，缺包时拒绝执行；升级专项只有一项，使用同一个测试自有资料目录。实际路径与最终通过结果见[1.0.0 验收](测试与CI.md)。普通修改先运行相关单元与短回归，涉及学习、采集、资料持久化或升级时，再运行三段场景。不能通过增加固定等待、跳过断言或自动重试，让失败的测试显示为通过。

Desktop 的 tests/daily-journey 保存场景，tests/helpers/business-clock.cjs 限制时钟路径，journey-evidence.cjs 保存检查点。Browser 使用独立的日常场景和真实扩展测试。测试资料只由各自 fixture 创建，清理只处理本次自有目录/进程。

升级验证要求升级前后版本递增、应用和 Jar 指纹不同、同一专属资料目录与兼容的数据结构。`schema 100` 数字相同不代表开发候选结构相同；现行启动同时核对完整结构。缺少可信且兼容的旧包时应明确报错，不能把同包重启冒充升级。首次 1.0.0 使用新的正式资料空间，未发布试用库原地保留；见[本地打包与安装](本地打包与安装.md)。

前一开发候选的源码与应用包曾分别通过 7/7 日常场景，并以 `1.0.0-dev.3` 完成一次隔离应用替换。这是旧候选结构的历史证据，不能证明清理旧实验表后的现行结构与旧包兼容。当前未发布候选不维护迁移；正式发布后的升级验证必须保留真实前一发行包及其资料，由对应版本用例验证。
